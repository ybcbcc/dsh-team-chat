# DSH Team Chat 协作与记忆开发说明

这次更新把团队保留在场景中，把目标、任务进度和交接放在各自的需求会话中。已有场景保留原团队配置。在团队设置里选「统筹模式」和「自动组队」，即可让 Owner 根据任务复用成员或补充角色。使用固定团队时，仍可指定 Owner 和每位成员的模型。

| 模式 | 适合的任务 | 交付路径 |
| --- | --- | --- |
| 置信 | 同一问题需要多个模型独立核实，再对照结论 | 初始问题和共有资料发送给各成员。先各自出结论，再核对争议、补证、汇总。到达所设轮数时，仍有分歧会留下具体争点和依据。 |
| 统筹 | 调研、开发、验收等阶段有先后关系，可以使用不同成员与强度 | Owner 提交依赖和验收条件，分工由插件发送，成员回报排队。Owner 按到达顺序或场景设置处理回报，给出简短交付结论。 |

## 执行与接续

- 发任务后，Owner 提交负责人、分工、依赖和验收条件。独立步骤并行，同一成员与同一工作区的写入按顺序执行。
- 默认按回报到达顺序唤醒 Owner。它处理一条回报时，其他回报继续入队。也可在场景里选择短时间合并或等当前阶段的成员回报。用户的「发送补充」进入同一队列。
- Owner 的后续决策仍会带入前面收到的用户补充和澄清答复，接续同一任务时也可读取。上下文记录来源编号、采用条数与因预算截取或省略的数量，完整记录可在原会话查看。子成员仍通过 Owner 收到相关指令。
- 成员只收到当前职责、任务和必要交接。要请另一个成员补查时，通过 Owner 转发。宿主记录实际派发、回复、转发、排队和决定。
- 同一转交只排队一次。时间线分别记录排队和实际下发，右栏成员聊天显示已下发的内容。任务已经启动时，后补内容可另派后续步骤。Owner 暂时不能提交有效决定时，已启动的成员先保存结果，供后续继续处理。
- 任务重试更新当前结果后，Owner 仍可转交已收到、且能定位到本场景和会话原消息的早期成员回报。尚未处理的回报继续排队。
- Owner 提前引用已排队的回报或用户补充时，对应的重试和转交暂缓，当前消息仍可处理。关停接续时，未读的失败回报保留在队列，等 Owner 读到后再安排。
- 任务结束条件包含必要步骤获验收、队列处理完毕和 Owner 提交最终交付。遇到依赖阻塞时，界面保留已完成步骤和具体卡点。通过「接续这项任务」可重用已验收结果，写入结果不确定时先只读核验。
- 同一成员反复失败时，Owner 可将该项交给另一位可执行成员。改派保留任务编号、依赖和历史尝试，写入结果仍需先核验。
- 上一轮在同一成员用尽尝试次数后结束时，接续会保留失败状态及最后一条回报，供 Owner 判断和改派。
- Owner 可说明依据并替换尚未启动任务的前置依赖。宿主检验引用与循环依赖，时间线保留前后差异。原来的必要任务仍需通过全局验收。
- Owner 处理回报期间，已安排的独立任务可在成员释放名额后继续启动。依赖步骤仍等待前置验收。等待澄清、校正无效决策或停止时暂停派发。
- 处理失败回报时，Owner 能看到原任务上已用尽尝试次数的成员，包括此前改派过的成员。再次选到该成员时，调度会给出仍有次数且满足任务权限的成员编号。
- 需要独立复核时，Owner 可安排另一位成员负责，并将开发交付列为前置任务。开发成员回报后，Owner 验收交付，宿主在依赖满足且有空闲成员时自动派发复核。复核可以只检查这次改动影响的项目。
- 等待外部资料时，可以设置最早查阅时间。例如上期所收盘后的结算文件可能晚于收盘发布，到点才开始查是否已经公布。等待期间，其他就绪步骤照常执行。仅余有时间限制的任务时，输入框显示「等待计划时间」。
- 更换工作目录后接续时，必须用新目录的证据重新确认前置任务。已有执行记录的写入步骤先只读核验，被引用的原任务和历史记录继续保留。
- Owner 的任务图显示每一步的读取或写入要求。已有适用的取证步骤时，沿用原任务和证据。需要新建独立账套、生成截图或保存报告时，可以安排获准写入的隔离步骤，明确目录和产物，再由原审查步骤核对。写入步骤接续时，宿主先只读核对断点，确认后进入写入阶段。

## 模型配置

自动组队的默认策略以 GPT-6.2 Sol 处理统筹和常规工作，GPT-6.1 Terra 优先处理需要视觉核对的任务，常规强度为 Medium。简单核对可用 Low，复杂任务提升档位。首选 Codex 模型不可用时，先检查成员已配置的模型，再从实际目录按 6.2、6.1、6.0、5.6 的顺序查找可用候选。同一代优先使用目录标为默认的模型。图片任务的自动路由会避开目录明确只支持文本等非图片输入的模型。DeepSeek 的默认搜索标记是 1017，也可在团队设置选实际接入的模型。回退理由和实际模型会保存在任务记录中。

Owner 可以在分工中指定成员的扩展档位，也可以由宿主按任务难度匹配。扩展档位沿用该成员的模型、供应商和技能，只调整思考强度。想固定没有扩展档位的成员配置，可以勾选「自动组队时沿用此成员的模型和强度」。

视觉输入与操作工具是不同能力。需要操作手机或浏览器的任务应使用已登记的相关技能，或在团队设置里明确当前环境已接好操作工具。更换模型不会改变成员身份或角色记忆。

## 查看历史

左侧回复下的「协作时间线」展示本轮协作事件，可展开和导出。右侧「本轮分工」可在下发前展开查看原始指令和验收要求，显示还需等待的前置任务、成员或同轮写入步骤。成员聊天按当前会话聚合，新任务会追加到旧记录后面。点击成员会加载该成员最近的交接，向前翻页时保留当前位置。需要对照时可开双窗并拖动中间分隔条，两栏各自翻页。历史按顺序号保存和恢复，模型只取本轮需要的内容。

## 上下文和数据流

「上下文」按成员和模型请求查看实际注入的角色、场景、记忆、技能、交接和历史。原生 DSH 运行还可从会话事件重建模型请求的组成。Codex 阶段展示插件组装的输入、可观测工具操作和服务端上报用量。点击趋势项可以联动内容浏览器，展开记录查看来源、文件活动和命令结果。

| 模块 | 关键职责 |
| --- | --- |
| `coordinator.js` | 执行依赖图、处理回报队列、接续历史分工、限制写入并发 |
| `workbench-host.js` 与 `model-routing.js` | 读取真实模型能力，调用各引擎，处理权限与 HTTP 接口 |
| `scenario-store.js` 与 `memory-compiler.js` | 持久化 SQLite 记录，增量整理会话摘要及附证据的记忆候选 |
| `context-insights.js` 与 `context-dashboard.js` | 收集可观测上下文、工具活动和用量，提供查阅与对照 |
| `workbench.js`、`workbench-views.js` 与 `workbench.css` | 呈现场景、右栏成员聊天、过程时间线和记忆管理 |

## 整理和复用记忆

新建需求会话并绑定同一场景后，Owner 和成员沿用原团队、已确认的共享记忆及自己的角色记忆。新会话从新的对话上下文开始。原会话的进度摘要也只在原会话中使用。

里程碑验收、任务收尾、收到引擎压缩通知和手动整理都可以触发增量整理。任务失败、未完成或带着分歧收尾时，也会从已保存的消息中提炼候选。主动停止的会话可按需点击「整理本会话」。引擎同时报告输入量和窗口容量时，输入用量达到窗口的 75% 也会触发。整理从上次处理的位置继续，使用插件已经保存的消息及消息附带的证据。新提案在记忆页确认后才参与常规调用。遇到同名冲突时可对照各自来源。

### 角色经验

| 类型 | 回答的问题 | 小红书发布角色的示例 |
| --- | --- | --- |
| 参考案例 | 做过什么类似任务，有哪些产物可以借用？ | 找到上次为同类商品准备的标题、封面和发帖步骤。 |
| 有效做法 | 什么条件下，哪个做法取得了可核对的结果？ | 发布后按账号、标题和商品卡逐项复核，可以发现挂错商品的情况。 |
| 踩坑与规避 | 当时出了什么问题，如何识别、预防或补救？ | 返回草稿继续编辑后，重新核对商品卡。页面显示改变时暂停并请审核角色复核。 |

上表是示例。实际条目保留适用条件、观察结果、下次动作和当时的证据。新会话按任务关键词从已确认的场景共享记忆与本角色经验中选取条目。

### 查看写入历史和原始对话

打开「记忆 → 写入历史」，可以按编号查找，例如输入 `#50`。每条记忆使用所在场景的稳定编号。时间线记录新增、改写、确认、归档和移除，显示版本、写入时间、触发方式与当时的内容摘要。有原消息时可展开摘录。写入时间和原消息时间分别显示，保留年份和秒。

记忆正文、修订、写入历史和插件内对话都保存在 `~/.dsh/codex-chat/scenarios.sqlite`。来源通过会话、任务和消息编号关联。点击历史中的会话名称，可以打开原任务，消息仍在时会定位到该条。原会话已解除绑定，或迁移后 DSH 找不到原生会话时，插件会在「历史会话来源」中打开仍存于数据库的对话。记忆详情保留「首次写入」的来源，在其他会话编辑过也能回查。要引用某条具体消息，可在该消息旁点击「存为记忆」，修改标题和正文，选择记忆层级和分类后保存。直接在记忆页新增时默认关联当前会话。旧资料和已经移除的原文，以保存下来的摘要及可用引用为准。迁移时复制场景数据库以保留插件内来源，原生 DSH 会话和工作区里的附件按各自位置迁移。

DSH-Context 的上下文成分、逐请求趋势和事件浏览适合用来查看整理前发生了什么。dsh-memory-evolve 的项目记忆、日志、归档及人工确认可用于对照长期记忆流程。OpenViking 的摘要到全文分层可用于对照如何先选相关记忆再查原文。 [DSH-Context](https://github.com/bowenliang123/dsh-context) · [dsh-memory-evolve](https://github.com/csyangwen/dsh-memory-evolve) · [OpenViking](https://github.com/volcengine/OpenViking)

## 运维边界

插件重载后，运行中的任务会标为中断。重新打开原会话并接续，可从保存的分工、回报和验收状态恢复。引擎未暴露的压缩内容无法从通知还原；整理会使用已持久化的证据。历史数据可迁移到新结构，旧记录中没有保存过的排队或转发时间不会补造。

插件使用 DSH 的 `DSH_HOME` 确定场景数据库和旧版聊天文件的保存位置。没有设置时使用用户目录下的 `.dsh`。在独立目录下运行测试用 DSH 实例时，可以让它使用自己的场景和会话数据。桌面版重载前先确认协作任务、记忆整理和旧版 `/codex` 调用已空闲。

随 DSH 提供的 Web 路由沿用宿主的登录和 Owner 权限。独立浏览器入口仅监听本机，核验连接地址、请求主机和浏览器来源。未提供 DSH 访问检查的旧宿主使用同样的本机限制。

Codex 的工作区自动审核由引擎的审核器处理。需要直接向客户端申请批准的操作，在自动审核模式下会被拒绝。人工审批模式在主聊天显示待批准的操作，完全权限模式只在该成员执行阶段应用。独立 Agent 接入还需要按其提供方配置实际的工具权限。
